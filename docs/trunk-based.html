Trunk-Based Development em cinco regras

O suficiente para trabalhar neste repositório sem atrapalhar as outras pessoas.

  1. 1. Uma linha só importa: a main

    A main está sempre publicável. Não existe develop, não existe branch de release. O que está na main é o que está no ar.

  2. 2. Integre pelo menos uma vez por dia

    Branch que vive mais de um dia vira dívida. Se o seu trabalho não cabe em um dia, quebre em pedaços que caibam — cada pedaço precisa deixar o site funcionando.

  3. 3. Commits pequenos e com contexto

    Um commit = uma mudança explicável em uma frase. Isso é o que torna possível reverter uma coisa sem desfazer outras cinco.

  4. 4. Puxe antes de empurrar

    git pull --rebase antes de cada git push. Conflitos resolvidos de dez em dez minutos são triviais; conflitos de duas semanas são um projeto à parte.

  5. 5. Quebrou a main? Conserta primeiro

    Se a CI ficar vermelha, a prioridade de todo mundo é voltar ao verde — corrigindo ou revertendo (git revert <sha>). Reverter não é fracasso, é higiene.

E quando a mudança é grande?

Duas técnicas resolvem quase tudo sem branch de longa duração:

Feature flag

Publique o código desligado e ligue depois. O código chega na main sem aparecer para quem visita o site.

const FLAGS = { novaSecaoQuiz: false };
if (FLAGS.novaSecaoQuiz) montarQuiz();

Branch curta

Precisa de revisão? Crie uma branch, abra o PR e integre no mesmo dia. Depois apague a branch.

git switch -c feat/secao-quiz
git push -u origin feat/secao-quiz
# abra o PR, integre, e:
git switch main && git pull --rebase

Comparando com o Gitflow

O que o Gitflow resolve bem

Software distribuído em versões (v1.2, v1.3), com suporte a versões antigas e janelas de release combinadas com clientes.

O que o trunk-based resolve bem

Produto que está sempre no ar — como este site. A "versão" é simplesmente o último commit da main.
